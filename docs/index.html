Why Touchbard

What the app gets from the runtime

Write a normal reactive UI. Touchbard handles getting it onto the physical strip — hardware, display and input included.

Real DRM/KMS

No framebuffer tricks. Discovery → resources → modeset → CPU scanout straight to the Touch Bar panel.

Keyboard & touch input

evdev readers with gesture recognition, udev hotplug and suspend/resume — multiple devices supported.

Memory-safe

Rust end to end. The DRM backend fails cleanly at initialize and never fabricates a display.

CPU only

Vello rasterizes to a premultiplied RGBA8 framebuffer — no GPU required on the machine.

60 Hz, event-driven

Frames are produced only when the document changes or animates; the loop idles the rest of the time.

Open source

A small set of workspace crates, built with cargo, auditable by anyone.

How it works

From USB to backlight, five steps

The pipeline the physical backends run at startup, in order.

USB preparation

The Touch Bar lives behind an Apple USB interface. Touchbard switches it into its display configuration so the kernel DRM driver binds to the panel.

vendor 0x05ac · product 0x8302 · USB config 2

Connector discovery

Find the DRM connector for the Touch Bar and read the authoritative physical dimensions from the device — 2008×60 landscape.

/dev/dri/cardN · sysfs

KMS resources & modeset

Allocate a transposed framebuffer (60×2008), set the mode, and let the driver attach it with a RIGHT_UP panel orientation.

drm_connector_set_panel_orientation(RIGHT_UP)

Render

Dioxus → Blitz → AnyRender → Vello CPU produces a landscape frame, which is mapped into the transposed buffer as it scans out.

dst(fx, fy) = src(fy, H − 1 − fx)

Present & wait

Present only when a new frame exists. Wake once per eventfd, suspend/resume via logind, and bound to 60 Hz while the UI animates.

eventfd wake · logind lifecycle
Render pipeline

One pipeline, shared by every display

The runtime renders into a premultiplied RGBA8 framebuffer; backends only consume frames.

touchbard::run
use touchbard::{Backend, TouchbardConfig};
use touchbard_drm::DrmBackend;
use touchbard_renderer::FrameSource;

// 1. initialize → authoritative Viewport, or fail cleanly
let backend = DrmBackend::new(DrmConfig::default());
let viewport = backend.initialize()?;   // 2008×60 landscape

// 2. runtime builds the UI system at exactly that viewport
let system = touchbard::system::System::new(viewport);
// 3. backend presents frames + feeds pointer/key events back
backend.run(system)?;
Dioxus→Blitz DOM/layout/style→AnyRender→Vello CPU→Frame RGBA8→DRM scanout

Rendering apps

Your folder is your route table

The Control Center example is a file-based app — routes are wired at compile time by app_router!(), no registry.

app/
app/ ├── layout.rs # root layout ├── page.rs # index route ├── settings/[section]/page.rs ├── docs/[...chapter]/page.rs ├── (admin)/dashboard.rs ├── not_found.rs # 404 └── error.rs # error boundary
hooks
  • use_navigate() — push a route
  • use_route() — current path
  • use_route_param(n) — dynamic segment
  • Nested layout.rs, route groups, catch-alls
  • Root not_found.rs / error.rs fallbacks
Development mirror. For desktop iteration a preview backend pipes the same frames to a browser over WebSocket — byte-identical pixels, no hardware attached. The DRM backend remains the production path.
